# ROOT-ADMIN 연동 계약과 확인 범위

확인일: 2026-09-23. 대상은 [ROOT-ADMIN 사이트](https://admin.roottale.com/site/gwangju2020-blog-madiclinic)와 `gwangju2020blog.madiclinic.co.kr`이다. 사용자 승인에 따라 사이트·관리자를 배포하고 운영 주소·팝업 슬롯·미리보기·메뉴 설정을 반영했다.

## 연결 계약

| 기능 | 정본과 동작 |
|---|---|
| 글·분류 | `cms/content-models.json`의 `column`·`reviews`·`faq`. 글과 분류는 CMS 공개 API에서 읽는다. 분류 slug를 코드에 고정하지 않는다. |
| 글 미리보기 | `/preview/post/{id}?token=…`. 세 모델 모두 실제 상세 화면을 재사용한다. ID와 토큰의 글이 일치해야 하며 초안을 영속 캐시에 저장하지 않는다. 메타데이터도 같은 검증 결과를 사용하고 검색 색인을 막는다. |
| 즉시 갱신 | `/api/revalidate`에서 ES256 서명을 확인한다. 모델별 글·목록·피드·사이트맵을 무효화하며, 칼럼 글 변경은 분류별 글 수 캐시도 무효화한다. |
| 팝업 | `cms/exposure-slots.json`의 `site-popup` 하나. `@roottale/cms-renderer-next`의 공용 Provider·Slot·노출 API를 사용한다. 서버 API 키는 브라우저에 전달하지 않는다. |
| 노출 위치 | `/column`·`/faq`·`/reviews` 첫 화면. 분류·상세·글 미리보기에는 표시하지 않는다. 자체 홈이 없으므로 세 경로를 공용 런타임의 `homePaths`로 전달한다. |
| 노출 조건 | ROOT-ADMIN에서 PC·모바일 이미지, 예약·종료 시각, 반복, 크기 등을 설정한다. 지원 표현은 `card`·`image-card`·`image`, 크기는 `small`·`medium`·`large`다. |
| 배너 | 페이지 상단의 사진 배너는 유지한다. CMS 홍보 배너 슬롯을 등록하지 않고 ROOT-ADMIN의 `banners` 메뉴만 숨긴다. `popups` 메뉴는 표시한다. |
| 루트 이동 | 일반 `/` 방문은 병원 홈페이지로 301. 관리자 팝업 미리보기는 루트 URL을 iframe으로 열기 때문에 해당 요청만 `/column`으로 307 이동해 같은 origin과 fragment를 유지한다. |

닫기·오늘 숨기기·여러 팝업의 순환·모바일 이미지 대체·미리보기 메시지 검증은 headnerve와 같은 공용 런타임이 담당한다. 팝업 조회는 서버가 정한 슬롯과 경로만 허용하고, 상류 오류는 비밀값 없이 503으로 응답한다.

공용 CMS의 캠페인 대상 `/`는 논리적인 첫 화면을 뜻한다. 슬롯의 `pathPrefixes`·`pathRules`에는 `/`의 정확한 일치를 허용하고, 실제 노출 주소는 `homePaths`의 세 커뮤니티 경로로 제한한다. 실제 주소를 `pathRules`에 대신 넣으면 관리자 발행 검증에서 거부된다. 운영 검수 중 이 불일치를 재현하고, 플랫폼의 실제 발행 검증·노출 판단 함수를 사용해 수정 전 실패와 수정 후 첫 화면 허용·상세 제외를 확인했다.

기존 설계상 로고·병원 정보·메뉴·푸터는 `src/data/{site,clinic,nav}.ts`와 마디 공통 컴포넌트에서 관리한다. ROOT-ADMIN의 사업장 정보·FRONT 구성·전역 글 표시 설정을 이 사이트가 읽는 구조는 아니다. 문의 폼·상담 게시판·디지털 명함도 이번 커뮤니티 연동 범위에 없다. 대행사에는 사용 가능한 세 콘텐츠 모델과 팝업 메뉴를 안내해야 하며, 관리자 전체 메뉴가 공개 사이트에 연결됐다고 안내하지 않는다.

## 발견한 문제와 수정

| 문제 | 조치 |
|---|---|
| 후기·FAQ 초안을 열어도 칼럼 전용 미리보기로 처리됨 | 모델별 상세 화면을 선택하는 공통 미리보기로 교체 |
| 제목 메타데이터 조회에 URL의 글 ID 검증이 빠짐 | 본문·메타데이터가 같은 ID 검증을 통과한 응답만 사용 |
| 칼럼 발행·삭제 후 분류별 글 수가 이전 캐시에 남음 | 글 웹훅에 `column:categories` 무효화 추가 |
| 팝업 조회 API·화면·슬롯 계약이 없음 | 공용 런타임과 팝업 슬롯 연결 |
| 팝업 관리자 미리보기의 `/`가 외부 병원 사이트로 이동함 | iframe 루트 요청의 내부 307 예외 추가 |
| 팝업 저장·미리보기는 되지만 발행 시 대상 페이지 검증에서 거부됨 | 슬롯의 논리적 첫 화면 `/`와 실제 `homePaths`를 구분해 계약 수정·동기화 |
| 관리자 Production URL이 비어 있음 | 운영 도메인 등록. 기존 웹훅 하나를 운영 대상으로 사용하며 중복 등록하지 않음 |
| 운영 관리자의 팝업·배너 숨김 설정이 통합되어 있음 | 개별 메뉴 기능 배포 후 이 사이트의 `banners`만 숨김 저장. `popups`는 유지 |
| 사이트에서 처리하지 않는 기본 `blog` 모델이 활성 상태 | 글이 없는 것을 확인한 뒤 비활성화 |
| 초안 발행 직후 수정하면 발행일이 빈 값으로 전송되어 저장 실패 | 서버가 확정한 발행일을 편집 상태에 반영. 같은 발행일의 재렌더에서는 입력 중인 값 유지 |
| 글 영구 삭제 뒤 목록만 갱신되고 분류가 포함된 상세 페이지가 남음 | 삭제 전에 공개 주소를 계산해 알림·outbox 재시도에 보관. 삭제 후 분류 연결을 다시 조회하지 않음 |

관리자 웹훅 화면에는 이전 24시간의 503·시간 초과·모델/경로 불일치 이력이 있었다. 과거 실패 수를 현재 진행 중인 장애로 보지 않는다. 최종 검수의 발행·수정·삭제 전송은 모두 성공했고 전달되지 않은 변경은 없었다. 이번 영구 삭제 오류는 웹훅 전송이 성공해도 상세 주소가 빠질 수 있는 사례였다. 전송 상태와 함께 실제 목록·상세 응답을 확인해야 한다. 기존 FAQ 웹훅 지연 수정은 [headnerve-copy.md](headnerve-copy.md)에 기록되어 있다.

## 검증 근거

| 범위 | 방법과 결과 |
|---|---|
| 실제 CMS 조회 | 세 모델의 발행 글·분류·모델·redirect·analytics·exposure API 조회 성공. 일부 API는 첫 요청 시간 초과 후 재조회에 성공했다. |
| 운영 공개 화면 | 기존 발행 상세 주소의 HTTP 200·제목·canonical 확인. 기존 글은 편집하지 않고 검수용 임시 글로 발행 흐름을 점검했다. |
| 로컬 서버 통합 | 운영 공개 콘텐츠의 사본과 가짜 사이트 키·서명 키로 production 서버를 실행. 세 모델의 목록·분류·상세·검색·페이지네이션·미리보기·XML, 발행/수정/삭제 웹훅과 실제 갱신을 확인했다. 모든 시나리오 통과. |
| 팝업 API | 세 첫 화면의 PC·모바일, 중지, 상세 제외, 슬롯·사이트 입력 변조 거부를 확인했다. |
| Aside 브라우저 | 같은 실행 호스트에서 PC 화면과 390·768·1280px iframe을 확인했다. 이미지 로드·모바일 이미지 선택·닫기·오늘 숨기기와 새로고침·스크롤 복구, 팝업 순환·CTA 이동, 가로 넘침과 헤더 겹침 여부를 확인했다. 사진 배너를 유지한 최종 화면에서도 팝업과 이미지가 정상 표시되고 가로 넘침이 없는지 확인했다. 루트 iframe의 내부 이동·fragment 보존과 미리보기에서 발행 팝업 조회가 중단되는 것도 확인했다. |
| 코드 검사 | `pnpm test`, `pnpm typecheck`, `pnpm build --webpack` 통과. 빌드는 별도 QA 사본에서 실행했다. |
| 슬롯 형식 | 플랫폼의 실제 발행 검증·노출 판단 함수로 첫 화면 허용과 상세 제외를 검증하고 운영 계약 version 2로 동기화했다. |
| 운영 팝업 | 관리자 PC·모바일 미리보기, 이미지 선택·저장·발행·제목 수정·표시 중지·영구 삭제를 확인했다. 실제 사이트에서도 기기별 이미지·닫기·오늘 숨기기·새로고침 유지·스크롤 복구와 상세 제외를 확인했다. 검수용 팝업은 삭제했다. |
| 운영 글 미리보기 | 칼럼·FAQ·치료후기 각각 실제 홈페이지 상세 화면과 `noindex, nofollow` 확인. FAQ 요약·상세 답변·추가 필드도 확인했다. 초안의 공개 상세 주소는 404이며 목록에 노출되지 않았다. |
| 운영 글 발행·수정·삭제 | 세 모델 모두 임시 글을 발행한 뒤 새로고침 없이 제목을 수정·저장했다. 목록의 제목과 상세의 제목·본문·canonical을 확인했고, 영구 삭제 뒤 목록에서 사라지며 상세가 404로 바뀌었다. 최종 검수에서는 수동 캐시 초기화 없이 자동 갱신됐다. |
| 관리자 회귀 검사 | 발행 직후 수정과 삭제 주소 유실을 수정 전 테스트로 재현했다. 수정 후 관리자 패키지 전체·타입 검사 통과. 기존 조건부 제외 테스트는 변경하지 않았다. |
| 배포 자동 검사 | 최종 관리자 커밋의 Playwright E2E·Quality Audit·Database CI가 모두 통과했다. |

검사별 결과와 집계의 원본은 `~/workspace/output/gwangju2020blog-madiclinic/2026-09-22-root-admin/`의 `http-results.json`, `production-read.json`, `candidate-vitest.log`, `candidate-build.log`, `candidate-typecheck.log`다. 커밋할 코드만 분리한 사본에서도 단위 검사·타입 검사·빌드를 확인했다. 가짜 CMS·HTTP 검사 스크립트와 QA 빌드 사본도 같은 폴더에 있다. 실제 시크릿은 복사하지 않았다. 브라우저 캡처는 같은 폴더의 `browser/`에 보관한다. 최종 사진 배너 유지 검증은 `final-related-tests.log`, `final-build.log`, `final-typecheck.log`, `final-photo-banner-http.json`과 `browser/final-*`를 따른다. ROOT-ADMIN 메뉴 분리 기능의 사이드바·저장·화면 검증은 `admin-menu-tests.log`에 있다.

사이트의 로컬 Playwright 테스트는 실행하지 않았다. 기존 스위트는 유지했으며, 실브라우저 동작은 같은 실행 호스트의 Aside로 확인했다. 로컬 서버로 확인하지 못했던 관리자 팝업 미리보기 메시지 연결은 운영 도메인에서 PC·모바일 모두 확인했다. ROOT-ADMIN CI의 기존 선택값 검증은 장식 아이콘까지 값으로 비교하던 부분을 바로잡았으며, 키보드·마우스 조작 검증은 유지했다.

운영 검수 원본은 같은 결과 폴더의 `production-post-lifecycle.jsonl`, `production-post-regression.json`, `production-faq-fields.json`, `production-popup-live.json`, `production-popup-cleanup.json`, `production-slot-regression.json`, `production-setup.json`이다. 최초 칼럼 삭제 오류와 임시 캐시 복구 기록도 보존했다. 수정본 배포 후 새 임시 글로 세 모델을 다시 검수했고, 검수용 글·팝업은 모두 영구 삭제했다. 기존 발행 글은 수정하지 않았다.

## 운영 설정

- 이번 연동 검수 배포: 사이트 `f9558fe`, 관리자 `7ec5b1d2`. 각 운영 도메인에 READY 상태로 반영한 뒤 검수했다.
- Production URL: `gwangju2020blog.madiclinic.co.kr`. 별도 Staging URL은 없다.
- 운영 웹훅: `https://gwangju2020blog.madiclinic.co.kr/api/revalidate` 하나를 활성화한다.
- 글 미리보기: 홈페이지에서 열기. 별도의 주소 재정의는 비워 둔다.
- 콘텐츠 모델: `column`·`reviews`·`faq`. 사용하지 않는 `blog`는 비활성화한다.
- 기본 메뉴: `banners` 숨김, `popups` 표시. 메뉴 숨김은 접근 권한 차단과 별개이며 공개 사이트는 팝업 슬롯만 허용한다.
- 팝업 슬롯 정본: `cms/exposure-slots.json`. 동기화는 플랫폼의 `packages/database/scripts/sync-site-content-contract.ts`에서 기존 모델·테마를 보존하는 슬롯 병합 경로를 쓴다. tenant/site ID는 [TODO.md](TODO.md)의 provision 항목을 따른다.

대행사는 팝업 메뉴에서 새 팝업을 작성하고 PC·모바일 미리보기를 확인한 뒤 표시한다. 실제 팝업은 별도 제작·발행해야 하며 검수용 팝업을 계속 노출하지 않는다.
